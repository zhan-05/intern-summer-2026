01测试概述与核心结论

1.1 报告目的

本报告记录一次针对 vLLM 推理框架 的系统性学习与测试实践。vLLM 是当前业界最主流的大语言模型（LLM）推理服务框架之一，本次工作围绕三个目标展开：

  • 技术学习： 理解 vLLM 的核心机制——PagedAttention、Continuous Batching 及其系统架构，并验证这些机制在真实运行中的表现；
  • 功能验证： 在本地环境完成 vLLM 的端到端部署，验证模型加载、文本生成、批量处理、对话生成等基础功能；
  • 性能度量： 设计标准化测试用例，采集吞吐量、延迟、内存占用等关键指标，建立可复现的性能基线。

本次测试在无独立 GPU 的 CPU 条件下进行。CPU 仅作为验证 vLLM 跨硬件后端能力的一种测试条件，本报告的分析重点始终是 vLLM 框架本身的技术特性、测试方法论与规律性结论。

1.3 核心结论摘要

✅ 功能可行性
vLLM 0.27.1 在 CPU 测试条件下全部 20 个执行单元成功通过，离线批处理 API（LLM.generate / LLM.chat）行为与官方文档一致，框架功能完整可用。
📊 性能基线（复测轮数据）
Qwen2.5-0.5B：单提示 22.8 tok/s、批量 16.8 tok/s、长生成 10.8 tok/s（92.6 ms/token）；SmolLM2-135M：单提示最高 64.2 tok/s。0.5B 模型在 4 核 CPU 上已可支撑近实时对话。
🔬 机制验证
实测印证了两条 vLLM 核心规律：① decode 阶段速度与参数量近似成反比（135M vs 500M 每 token 耗时 33.6ms vs 92.6ms，比值≈1/2.75，与参数量比 1/3.7 基本吻合）；② 批量场景下连续批处理使高 token 产出模型的吞吐反超（Qwen 批量 16.8 tok/s > SmolLM2 的 8.7 tok/s）。
⚠️ 工程注意

02vLLM 核心原理

2.1 框架定位与技术背景

vLLM 由加州大学伯克利分校 Sky Computing Lab 开源，论文发表于系统领域顶级会议 SOSP 2023，现已成长为 LLM 推理与服务的事实标准框架之一。其设计目标是：在保持模型精度的前提下，最大化推理吞吐量与显存利用率。相对 HuggingFace Transformers 的朴素实现，vLLM 的典型吞吐量提升可达 14-24 倍。

vLLM 解决的核心矛盾是：LLM 推理对 KV 缓存的需求是动态且不可预测的，而传统推理框架按最大长度静态预留，导致 60-80% 的缓存空间被浪费。围绕这一矛盾，vLLM 给出了两项关键创新。

2.2 LLM 推理的两阶段过程

理解 vLLM 的优化，需要先理解 LLM 推理的两个阶段：

阶段工作内容计算特征性能瓶颈
Prefill并行处理输入 prompt 的所有 token，生成首 token矩阵×矩阵（GEMM），并行度高计算能力（Compute-bound）
Decode每次迭代生成一个 token，直至结束矩阵×向量（GEMV），并行度低访存带宽（Memory-bound）

Decode 阶段每生成一个 token，都需要完整读取一遍模型权重（如 0.5B 模型 BF16 约 1GB）。这意味着 decode 速度理论上受限于内存带宽：带宽 50 GB/s ÷ 权重 1 GB ≈ 50 tok/s 的上限。本测试的实测值（Qwen2.5-0.5B 长生成 10.8 tok/s）低于该理论上限，说明还存在调度、Python 开销等额外瓶颈（详见 6.4 节）。这一"访存受限"特性也解释了为什么 batching 是推理框架的第一要务——多个请求共享同一份权重读取，可成倍提高有效吞吐。

2.3 核心创新一：PagedAttention

2.3.1 问题：静态预留导致的缓存碎片

传统推理框架为每个请求按最大可能生成长度连续预留 KV 缓存空间。由于实际生成长度通常只占预留的 20-40%，造成：

  • 内部碎片： 预留 2048 token 空间实际只用了 300；
  • 外部碎片： 频繁分配释放后，剩余空间虽总量足够却无法连续分配；
  • 后果： 缓存利用率仅 20-40%，直接限制了并发 batch 的规模。

2.3.2 方案：操作系统式分页管理

PagedAttention 借鉴操作系统虚拟内存分页机制：将 KV 缓存切分为固定大小的 block（默认 16 token/块），请求通过块表（block table）映射到物理上非连续的块，按需分配、用完即还：

传统连续分配（利用率低）          PagedAttention 分块分配（利用率高）
┌────────────────────┐          物理块池: [A0][B0][A1][C0][B1][A2] ←块可非连续
│ Request A ████░░░░░│          块表 A: [0, 2, 5]   ←逻辑连续、物理离散
│ Request B ███░░░░░░│          块表 B: [1, 4]
│ Request C ██░░░░░░░│          块表 C: [3]
└────────────────────┘          ░ = 浪费空间 █ = 实际使用
  ░░≈60-80%被浪费                  几乎无碎片，利用率 80-95%

2.3.3 收益

  • KV 缓存空间利用率从 20-40% 提升至 80-95%；
  • 同样内存可容纳更多并发请求，间接放大 batch 规模与吞吐；
  • 支持写时复制（Copy-on-Write）：相同前缀的请求共享物理块，配合 Prefix Caching 进一步节省（多轮对话 TTFT 降低 50-80%）。

2.4 核心创新二：Continuous Batching

2.4.1 问题：静态批处理的队头阻塞

传统 static batching 要求整批请求全部完成后才能开始下一批。若批内一个请求生成 500 token，其余 50 token 即完成，短请求也只能空等，硬件利用率低下：

Static Batching（整批同步）              Continuous Batching（token 级调度）
iter1 [A B C D]                          iter1 [A B C D]
iter2 [A B C D] ← D 已完成却仍占位        iter2 [A B C D] → D 完成，立即移出
iter3 [A B C D]                          iter3 [A B C E] ← 新请求 E 即刻加入
iter4 [E F G H] ← 新批等整批结束          iter4 [A B F E] ← C 完成，F 加入
                                         …  硬件始终满载

2.4.2 收益

调度粒度从"批"细化为"单次 token 迭代"，已完成请求即刻让位、排队请求即刻补位。vLLM 论文实测该机制带来 8-23 倍吞吐提升；本测试第六章的批量用例也将展示其效果（Qwen2.5-0.5B 批量 10 请求时吞吐 16.8 tok/s，未出现严重性能坍缩）。

2.5 系统架构分层

vLLM 采用清晰的分层架构，上层 API 在不同硬件后端间完全一致——这是本次 CPU 测试的前提：切换后端不影响应用代码：

┌───────────────────────────────────────────────┐
│  API 层：LLM（离线）/ AsyncLLMEngine / OpenAI Server │
├───────────────────────────────────────────────┤
│  Engine 层：LLMEngine V1                          │
│    · Scheduler（调度器，实现 Continuous Batching）   │
│    · BlockManager（块管理器，实现 PagedAttention）   │
├───────────────────────────────────────────────┤
│  Executor 层（可插拔硬件后端）                      │
│    GPUExecutor │ CPUExecutor │ OpenVINO │ TPU …   │
├───────────────────────────────────────────────┤
│  Model 层：ModelRunner + 200+ 模型实现             │
│    Qwen2 / Llama / Mistral / Gemma / …           │
└───────────────────────────────────────────────┘

2.7 推理性能的底层决定因素

综合上述原理，LLM 推理框架的性能可归纳为四个决定因素，它们也构成本测试的分析框架：

因素机制对应测试观察点
① 参数量 × 精度决定 decode 每步的权重读取量（访存瓶颈）两模型 ms/token 差异（6.4 节）
② 批处理效率权重读取在并发请求间摊薄，提升有效吞吐批量 vs 单提示吞吐变化（6.4 节）
③ 缓存管理利用率决定可并发规模；耗尽触发抢占重算批量用例输出长度差异（5.2 节）
④ Prefill/Decode 配比短输出请求中 prefill 占比高，拉低表观吞吐对话用例的吞吐异常（6.4 节）

3.1.3 CPU 指令集条件

vLLM CPU 后端在启动时自动探测指令集并选择最优内核。本条件支持 AVX512 + VNNI（中高档），不支持更新的 AVX512_BF16 与 AMX（需 Sapphire Rapids 及以后），意味着 BF16 由软件模拟执行——这也是实测每 token 耗时高于官方参考值的原因之一：

指令集状态与 vLLM 的关系
SSE4.2 / AVX2支持vLLM CPU 后端的最低运行要求
AVX512 / F16C支持512 位向量运算，主要 GEMM 内核基础
VNNI支持INT8 点积加速，量化推理的前提
AVX512_BF16不支持BF16 原生 GEMM，缺失时软件模拟（约 30% 性能差）
AMX不支持硬件矩阵扩展单元，缺失时 GEMV 效率受限

部署过程共记录 8 个问题，覆盖依赖管理、网络、配置三个类别。全部问题均已定位根因并获得可复现的解决方案，这也是本次测试的重要工程产出：

编号问题现象根因分析解决方案

⭐ 关键工程结论（P6）
资源受限环境下部署 vLLM 的成败取决于内存预算三要素：引擎常驻开销（约 0.8-1.0 GB）+ 模型权重（BF16 ≈ 2×参数量）+ KV 缓存（VLLM_CPU_KVCACHE_SPACE）。三者之和必须低于物理内存的 85%，且 KV 缓存建议取总内存的 25-40%。

6.4 关键发现与归因分析

发现 ① decode 速度与参数量近似成反比

TC5 纯 decode 场景下，两模型每 token 耗时 33.63 ms vs 92.59 ms，比值 2.75×；参数量比 3.7×。差距未达 3.7× 的原因是固定开销（调度、Python 层、内核启动）在 135M 模型的 33.63 ms 中占比更高。该发现印证 2.2 节原理：decode 是访存受限操作，权重读取量（参数量×精度）直接决定速度下限。

发现 ② 批量场景下"质量好的模型吞吐更高"

TC3 中 Qwen 吞吐（16.78）反超 SmolLM2（8.69），直接原因是 token 产出 640 vs 197：SmolLM2 在 temperature=0.7 下频繁输出空串或 1-12 tokens 即提前终止。深层机制是 vLLM 的 Continuous Batching 按实际生成的 token 摊薄权重读取成本——生成内容越充实，批量加速效果越明显。对框架的启示：评估批吞吐必须固定 token 产出口径，否则结论失真。

发现 ③ 短输出用例中 prefill 占比扭曲表观吞吐

TC4 对话用例 Qwen 吞吐仅 7.60 tok/s（低于其 TC5 的 10.80），并非引擎退化，而是 3 段对话共只产出 28 tokens——prefill（处理 system 模板与输入）耗时占比过高，公式"吞吐 = tokens ÷ 总耗时"的分母被 prefill 主导。这验证了 2.7 节因素④：跨用例比较吞吐必须控制输出长度。生产服务中对应的优化手段是 Chunked Prefill 与 Prefix Caching（system 模板 KV 复用）。

发现 ④ 实测吞吐距带宽理论上限仍有空间

Qwen2.5-0.5B 的 BF16 权重约 1 GB，DDR4 带宽约 50 GB/s，理论上限约 50 tok/s；实测 10.8 tok/s（约 22%）。缺口来源：无 AMX/AVX512_BF16 导致的软件模拟、EngineCore 与 Worker 间 ZMQ 进程通信、Python 调度开销、以及未启用 TCMalloc/libiomp。这为第八章优化路线提供了量化依据。

发现 ⑤ 内存水位是稳定性红线

Qwen 加载后系统水位 82.7-87.8%（两轮），继续叠加任何大内存操作（如切换模型、高并发批量）都有 OOM 风险。两模型 RSS 增量（352/369 MB）远小于权重体积，说明 vLLM 通过子进程与按需加载管理内存，但系统级水位监控比进程 RSS 更能预警风险。

7.3 对 vLLM 核心机制的验证

本次测试的最终价值在于将第二章的原理知识转化为可观测证据：

  • PagedAttention 验证： 2 GB KV 缓存（约可容纳 Qwen 0.5B 的 8700+ tokens）支撑了 10 请求并发的批量用例全程无抢占报错，块化管理在有限内存下维持了调度稳定；
  • Continuous Batching 验证： 批量 10 请求时 Qwen 吞吐（16.78）未低于其单流水平（10.80），并发没有造成性能坍缩，权重读取在请求间有效摊薄；
  • API 后端解耦验证： 测试代码未使用任何 CPU 专属 API，同一脚本可直接迁移至 GPU 环境，印证了架构分层的工程价值；
  • 访存受限模型验证： ms/token 与参数量的强相关性（发现①）与两阶段理论的预测一致。

  • 内存预算先行： 部署前按"引擎常驻 + 权重 + KV 缓存 ≤ 物理内存 85%"做预算，KV 缓存取总内存 25-40%；
  • 性能口径标准化： 吞吐对比必须固定输出 token 数与并发度，区分 prefill 主导与 decode 主导场景（本报告发现②③的教训）；
  • 多轮取区间： 共享环境单次测试波动可达 ±50%，基线数据应至少两轮并报告区间；
  • 固定数据留痕： 测试脚本应始终落盘 JSON 全量明细（本项目的 results.json 模式），保证结论可溯源；
  • 依赖问题固化： 将 --no-deps 安装顺序、镜像配置写入安装脚本（install_vllm_v3.sh），避免后人重踩 P2-P4。
