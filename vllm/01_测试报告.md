**报告类型：** 技术复现报告（Reproduction Report）

## 一、问题描述（Problem Description）

### 1.1 复现背景

vLLM 是当前业界主流的大语言模型（LLM）推理服务框架，其官方文档与性能数据均基于 GPU 环境给出。对于无独立 GPU 的开发与学习场景，vLLM 提供了独立的 `vllm-cpu` 发行包作为 CPU 执行后端，但该路径存在以下未明确的问题：

1. **可用性未知：** `vllm-cpu` 包能否在普通 Intel 消费级 CPU 上正常加载模型并完成推理，缺乏公开的端到端验证记录；
2. **部署门槛未知：** 文档未充分说明在资源受限（低内存、无 GPU）环境下的依赖冲突与配置要求；
3. **性能基线缺失：** CPU 模式下小参数模型的吞吐量、延迟、内存占用等关键指标无公开可复现数据；
4. **质量边界未知：** 多大参数量的模型在 CPU 上仍能产出可用输出，缺乏实测对照。

### 1.2 复现目标

本报告旨在以可复现的工程方法回答以下问题：

| 编号 | 问题 | 验证方式 |
|---|---|---|
| Q1 | vLLM 0.27.1 能否在纯 CPU + WSL 环境完成端到端推理？ | 执行 5 类测试用例，记录通过/失败 |
| Q2 | 部署过程存在哪些阻断性问题及解决方案？ | 全程记录问题清单与修复步骤 |
| Q3 | 小参数模型（135M / 500M）在 i5 CPU 上的性能指标？ | 采集吞吐量、延迟、内存、每 token 耗时 |
| Q4 | 实测结果与理论预期/官方参考值的差距及归因？ | 对照带宽理论上限与官方数据做差异分析 |
| Q5 | 哪些场景下 CPU 模式具有实用价值？ | 基于质量-速度权衡给出场景评级 |

### 1.3 复现范围

- **被测对象：** vLLM 0.27.1（vllm-cpu 发行包）离线批处理 API（`LLM.generate` / `LLM.chat`）
- **测试模型：** HuggingFaceTB/SmolLM2-135M-Instruct、Qwen/Qwen2.5-0.5B-Instruct
- **测试用例：** 模型加载、单提示生成、批量请求、对话生成、长文本生成共 5 类
- **执行轮次：** 2 轮独立执行，用于评估波动与可复现性

## 三、复现步骤（Reproduction Steps）

### 3.1 总体流程

```
Windows 11
   └── WSL2 Ubuntu 26.04 LTS
        ├── Python 3.14.4（系统自带）
        ├── venv 虚拟环境（~/vllm-env）

        │    ├── vllm-cpu 0.27.1
        │    └── 全部 vLLM 依赖
        └── HF 模型缓存（~/.cache/huggingface/）
```

### 3.2 步骤 1：安装系统依赖

```bash
sudo apt-get update
sudo apt-get install -y python3-pip python3-venv libnuma-dev libtcmalloc-minimal4
```

### 3.3 步骤 2：创建 Python 虚拟环境

```bash
python3 -m venv ~/vllm-env
source ~/vllm-env/bin/activate
pip install --upgrade pip wheel setuptools
```

### 3.4 步骤 3：安装 PyTorch（使用清华镜像加速）

```bash
pip install -i https://pypi.tuna.tsinghua.edu.cn/simple torch==2.13.0
```

### 3.5 步骤 4：安装 vllm-cpu（使用 --no-deps 规避依赖冲突）

```python

    "HuggingFaceTB/SmolLM2-135M-Instruct",
    "Qwen/Qwen2.5-0.5B-Instruct",

    snapshot_download(
        repo_id=model_id,
        allow_patterns=["*.json", "*.safetensors", "*.txt", "tokenizer.model", "*.model"],
    )
```

- SmolLM2-135M-Instruct：260 MB / 35 秒 = **7.3 MB/s**

## 六、差异分析（Expected vs Actual）

### 6.1 性能差异归因

**差异 1：实测吞吐低于带宽理论上限**

| 模型 | 理论上限 | 实测（复测轮） | 达到率 | 缺口来源 |
|---|---|---|---|---|
| Qwen2.5-0.5B | ~50 tok/s | 10.80 tok/s | 22% | 无 AMX/AVX512_BF16 软件模拟、ZMQ 进程通信、Python 调度开销、未启用 TCMalloc |
| SmolLM2-135M | ~185 tok/s | 29.74 tok/s | 16% | 同上 + 固定开销在小模型占比更高 |

**差异 2：每 token 耗时比值（2.75×）低于参数量比（3.7×）**

原因：调度、Python 层、内核启动等固定开销在 135M 模型的 33.63 ms 中占比更高，拉低了参数量比值。

**差异 3：批量场景下 Qwen 吞吐反超 SmolLM2（与"小模型更快"直觉相反）**

直接原因：token 产出量 640 vs 197。SmolLM2 在 temperature=0.7 下频繁输出空串或 1-12 tokens 即终止。
深层机制：vLLM Continuous Batching 按**实际生成的 token** 摊薄权重读取成本——生成内容越充实，批量加速效果越明显。

**差异 4：对话用例 Qwen 吞吐（7.60）低于其长生成吞吐（10.80）**

原因：3 段对话共只产出 28 tokens，prefill（处理 system 模板与输入）耗时占比过高，公式"吞吐 = tokens ÷ 总耗时"的分母被 prefill 主导。非引擎退化。

**差异 5：两轮测试数据波动达 ±50%**

| 指标 | SmolLM2 基线→复测 | 波动 | Qwen 基线→复测 | 波动 |
|---|---|---|---|---|
| TC2 单提示吞吐 | 40.55 → 64.22 | +58% | 15.19 → 22.81 | +50% |
| TC5 长生成吞吐 | 17.17 → 29.74 | +73% | 9.01 → 10.80 | +20% |
| 加载时间 | 30.89 → 30.40 s | -2% | 39.70 → 28.69 s | -28% |

原因：基线轮系统水位更高（后台负载较大），导致吞吐整体偏低；加载时间相对稳定。
结论：共享内存环境中单次测试不足以定论，性能基线应报告为区间值。

### 6.2 质量差异归因

Qwen2.5-0.5B 以约 1/2.75~1/3.7 的速度代价换取了从"不可用"到"实用"的质变。在 0.5B-1B 量级选择 CPU 推理模型时，应优先保证质量下限，再追求速度——速度缺口可通过量化（INT8）与运行时优化补偿，而质量缺陷无法在推理侧修复。

## 七、遇到的问题与解决方案（Issues & Solutions）

部署过程共记录 8 个问题，全部已定位根因并获得可复现的解决方案：

| 编号 | 问题现象 | 根因分析 | 解决方案 |
|---|---|---|---|
| P1 | Python 3.14 兼容性疑虑 | vllm-cpu wheel 采用 cp38-abi3 稳定 ABI，官方文档仅写到 3.12 | 实测可用，无需降级 Python |
| P2 | `torch==2.13.0+cpu` 版本不存在，安装中断 | vllm-cpu 依赖声明过时；PyTorch 2.7 起已改用统一 wheel（无 +cpu 后缀） | 先装 torch 2.13.0，再 `--no-deps` 装 vllm-cpu，手动补齐其余依赖 |
| P3 | PyPI 下载 28 KB/s | 默认源 CDN 链路质量差 | 切换清华镜像，提速 280 倍至 7.8 MB/s |
| P4 | HF 模型下载 401 Unauthorized | 镜像站不支持 Xet 协议 | `HF_HUB_DISABLE_XET=1` 回退 HTTP 下载 |
| P5 | `gpu_memory_utilization=0.0` 触发 pydantic 校验失败 | 参数校验要求 > 0，与 CPU 模式用法直觉冲突 | 移除该参数，CPU 后端自动忽略 |
| P6 | KV 缓存请求 8 GB 超出可用内存，引擎启动失败 | 7.6 GB 内存扣除引擎常驻后仅余 3.7 GB | `VLLM_CPU_KVCACHE_SPACE=2` + `max_model_len=1024` 精细化内存预算 |
| P7 | Triton 不可用警告 | Triton 为 GPU JIT 编译器，CPU 无驱动 | 无需处理，vLLM 自动降级 V1 Runner |
| P8 | libtcmalloc / libiomp 未预加载警告 | 性能库可提升多线程内存分配与调度效率 | 预留优化项，基线测试保持未启用 |

> **关键工程结论（P6）：** 资源受限环境下部署 vLLM 的成败取决于**内存预算三要素**：引擎常驻开销（约 0.8-1.0 GB）+ 模型权重（BF16 ≈ 2×参数量）+ KV 缓存。三者之和必须低于物理内存的 85%，KV 缓存建议取总内存的 25-40%。

3. `VLLM_CPU_KVCACHE_SPACE` 不得超过总内存的 40%（问题 P6 教训）
4. 不要设置 `gpu_memory_utilization=0.0`（问题 P5 教训）
5. 性能数据应至少两轮取区间，单次结果波动可达 ±50%

## 九、结论与建议（Conclusions & Recommendations）

### 9.1 复现结论

| 维度 | 评级 | 结论 |
|---|---|---|
| 功能完整性 | 通过 | 20/20 执行单元零失败；API 行为符合官方语义；Llama/Qwen2 双架构加载正常 |
| 性能水平 | 达基线 | Qwen2.5-0.5B：长生成 9-11 tok/s，批量 13.5-16.8 tok/s；SmolLM2-135M：长生成 17-30 tok/s |
| 输出质量 | 分化 | 0.5B 模型全面可用；135M 模型仅可用于功能冒烟验证 |
| 工程成熟度 | 可用但需经验 | 部署存在 8 个需人工解决的问题，非开箱即用；解决后流程完全可复现 |

### 9.2 适用场景评级

| 场景 | 推荐度 | 依据 |
|---|---|---|
| 学习 vLLM 原理与 API 开发 | 强烈推荐 | API 与 GPU 版本完全一致，全部核心机制可实地观察 |
| 应用开发调试 / CI 冒烟 | 推荐 | 4 分钟即可完成 5 用例回归，seed 固定输出可复现 |
| 小规模离线批量处理 | 推荐 | 批量 13.5-16.8 tok/s，连续批处理有效摊薄成本 |
| 个人本地对话（0.5B 模型） | 勉强可用 | 10.8 tok/s 下 50 token 回复约需 4.6 秒 |
| 生产高并发服务 | 不推荐 | 算力/带宽缺口 5-10 倍，无法满足 SLA |
| ≥1B 参数模型推理 | 不可行 | 7.6 GB 内存无法容纳权重 + KV 缓存的安全组合 |

### 9.3 改进建议

1. **启用 TCMalloc + Intel OpenMP**：预加载 libtcmalloc 和 libiomp5.so，预计提升 10-30% 性能
2. **模型量化**：使用 INT8 或 U8 权重压缩，可将 Qwen2.5-0.5B 内存占用从 1 GB 降至 300 MB
3. **使用 OpenVINO 后端**：编译 vLLM 的 OpenVINO 分支，对 Intel CPU 有针对性优化
4. **限制上下文长度**：将 `max_model_len` 控制在 512-1024，减少 KV 缓存压力
5. **增加物理内存**：升级到 16 GB RAM 后可运行 1-3B 参数模型
6. **使用云 GPU 替代**：对于生产负载，建议使用云端 GPU 实例
